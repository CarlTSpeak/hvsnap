# hvsnap v3 — what's new

v3 extends hvsnap's capture format with a **second sidecar** and a driver
extension. Everything from before is unchanged: the Pinscan-format snapshot,
`hvtrace.json`, `snapshot.ext.json` (v2 sidecar) are written exactly as they
were, and the tool, driver, service and device names are `hvsnap`.

## The new output: `snapshot.ext3.json`

Written last, beside the existing files, schema
`slf.hvtrace.snapshot-ext.v3`. Skip it with `--no-ext3` (the v2 sidecar is
always written). Sections:

| Section | What it adds | Provenance |
|---|---|---|
| `cpu_identity` | the measured **CPUID leaf-0 vendor string** (ASCII + raw 12 bytes), `max_leaf`, `max_extended_leaf`, and `family`/`model`/`stepping` decoded from leaf 1 (display form). Leaf 0 was the one CPU fact the engine's vendor-law selection had never measured. | `host_cpu_enumeration` |
| `tsc_calibration` | leaves **0x15** (core:ref clock ratio, nominal TSC Hz) and **0x16** (base/max/bus MHz) — makes `tsc_guest_visible` convertible to wall time. Zeros are reported as not-enumerated, never guessed. | `host_cpu_enumeration` |
| `descriptor_tables` | **GDTR/IDTR/LDTR/TR** (base, limit, and for LDTR/TR the hidden descriptor-cache attributes and selectors) as measured in the hypervisor exit of the freeze — exactly what SGDT/SIDT/SLDT/STR would have returned at the frozen instruction. Against a pre-v3 driver the section is `absent` (the driver reports how much it filled; nothing is zero-filled). | `same_hit_guest` |
| `fp_state_upper` | the **XSAVE features beyond x87/SSE**: YMM upper halves (`ymm0_upper`..`ymm15_upper`), and on AVX-512 hosts `k0..k7`, `zmm*_upper`, `zmm16..31` — read via `CONTEXT_XSTATE` + `LocateXStateFeature` from the parked thread. | `parked_thread_context` |
| `integrity` | **sha256 + size of every file** in the snapshot directory (self-excluded, written last). A capture can now verify itself. | computed |

## New CLI flag

```
--no-ext3    (snapshot) skip the v3 sidecar (snapshot.ext3.json); the
             v2 sidecar (snapshot.ext.json) is always written.
```

## Driver extension, and why old and new mix safely

The driver captures the descriptor-table registers in the park handler (they
live in the VMCB state-save area) and returns them as a third tier of
`HVSNAP_STATE`:

- tier 1 — core status, gated by `HVSNAP_STATE_V1_SIZE` (48)
- tier 2 — measured same-hit state (segment bases … CR8), gated by
  `HVSNAP_STATE_V2_SIZE` (232)
- tier 3 — descriptor tables, gated by the full struct

QUERY fills exactly what the caller's buffer allows and reports the byte
count, so an old controller keeps working against a new driver, and a new
controller against an old driver sees `descriptor_tables: absent` instead of
zeros. v2 emission is untouched.

## The executables

| File | Built by | What it is |
|---|---|---|
| `hvctl\hvctl.exe` | `hvctl\build-hvctl.cmd` (VS2026 x64, no admin) | the controller. Modes `freeze` / `snapshot` / `debug` / `trace` (`trace-tocsv`, `cloak-off`); all options in `DOCUMENTATION.md` §6. v3 adds `--no-ext3`. Runs without elevation once the driver is loaded. |
| `hvctl\probe.exe` | `hvctl\build-probe.cmd` | standalone "when does this VA become mapped/executable" diagnostic (no driver needed). |
| `x64\Release\hvsnap.sys` | `MSBuild hvsnap.sln /p:Configuration=Release /p:Platform=x64 /p:SignMode=Off` | the kernel driver. Sign + load + unload via `tools\sign-hvsnap.ps1` / `load-hvsnap.ps1` / `unload-hvsnap.ps1` (elevated). Service name `hvsnap`, device `\\.\hvsnap`. |

First capture:

```powershell
hvctl\hvctl.exe snapshot --launch "C:\path\to\target.exe" --rip 0x140001000 --out C:\dumps
# -> C:\dumps\snapshot_full_hv_000_rip140001000\{hvtrace.json, regs.txt,
#    region_*.bin, manifest.txt, snapshot.ext.json, snapshot.ext3.json}
```

## Validation status

**Hardware-validated on the capture host (AMD Ryzen 9 5950X) since
2026-11-13**: the v3 driver is signed, loaded and the live capture driver
(replacing the `hvtrace` service, which stays registered but stopped). First
capture caught three hvctl emitter defects (model bitfield, YMM row-name
aliasing, a JSON separator — fixed in `z/ext3-emit-fixes`); the driver's
descriptor-table tier was correct on the first try. The validation capture
(`snapshot_full_g1b_000_rip402630`): valid JSON, `AuthenticAMD` family 25
model 33 stepping 0, `ymm0_upper..ymm15_upper` distinct, descriptor tables
sane (GDTR/IDTR kernel bases, LDTR 0, TR selector 0x40 attrib 0x89),
`tsc_calibration` honestly absent (leaves 0x15/0x16 not enumerated on this
CPU), and all 72 integrity sha256s re-verified against an independent hash.
Build hygiene unchanged (SHA-256: 11/11 vectors vs hashlib).
